# Dataset Package — сторона потребителя

Как ModelArena читает `dataarena.package/1`.

**Владелец контракта — DataArena** ([D-11](../DECISIONS.md#d-11-владелец-контракта-dataset-package--dataarena)).
Исходная спецификация: [DataArena/docs/contracts/dataset-package-v1.md](../../../DataArena/docs/contracts/dataset-package-v1.md).
Сверка двух независимых предложений: [RECONCILIATION.md](../../../DataArena/docs/contracts/RECONCILIATION.md).

Этот документ — **обязательства потребителя**. Он не меняет контракт; замечания к контракту
собраны в §7 и передаются владельцу.

---

## 1. Что ModelArena обязана уметь

| Обязательство | Проверяется тестом |
|---|---|
| Прочитать пакет, ни разу не импортировав код DataArena | анализ импортов в CI |
| Отвергнуть неизвестную мажорную версию с внятным сообщением | `test_unknown_major_version_rejected` |
| Проверить `sha256` каждой части до её использования | `test_corrupted_part_rejected` |
| Игнорировать незнакомые поля, а не падать на них | `test_unknown_fields_ignored` |
| Работать без опциональных частей (`profile`, `lineage`, `recipe`) | `test_minimal_package_reads` |
| Показать `hints` как подсказки, не выбирая target автоматически | `test_hints_do_not_autoselect_target` |
| Показать плашку при `profile.computed_on.sampled: true` | frontend-тест |
| Работать вообще без DataArena | `test_standalone_import` |

## 2. Алгоритм чтения

```
1. открыть пакет (каталог или .dapkg.zip; zip — с лимитом на размер и число файлов)
2. прочитать manifest.json
   ├─ format != "dataarena.package"            → отказ
   ├─ major(format_version) != 1               → отказ с текстом, какая версия понимается
   └─ отсутствует data.files или data.sha256   → отказ
3. для каждой используемой части: сверить sha256 → несовпадение → отказ, чтение прекращается
4. прочитать data/*.parquet (все части, в порядке из manifest) → одна таблица
5. сверить фактическое число строк с data.row_count
   └─ расхождение при row_count_exact: true    → отказ
      расхождение при row_count_exact: false   → предупреждение, работа продолжается
6. прочитать schema.json (если есть) → сопоставить с фактическими dtype из parquet
7. прочитать profile.json / lineage.json / recipe.json (если есть) → сохранить как есть
8. записать снимок: artifacts/datasets/<dataset_id>/data.parquet + meta.json
9. посчитать СВОЙ fingerprint = sha256(схема || содержимое)
10. посчитать СВОЙ профиль колонок
```

Шаги 9 и 10 обязательны: чужой `sha256` подтверждает целостность файла, но идентичность
снимка внутри ModelArena определяется её собственным отпечатком, а решения — её собственными
числами ([D-9](../DECISIONS.md#d-9-dataarena-hints-и-profile--advisory-only)).

## 3. Отображение пакета в домен ModelArena

| Из пакета | Куда | Как используется |
|---|---|---|
| `data/*.parquet` | `DatasetSnapshot.data` | единственный источник истины о данных |
| `manifest.package_id`, `name`, `producer` | `DatasetSnapshot.package_ref` | карточка датасета, происхождение |
| `manifest.data.sha256` | проверка целостности | не заменяет собственный fingerprint |
| `schema.columns[].semantic_type` | стартовая гипотеза о типе колонки | подтверждается фактическим dtype; при расхождении выигрывает parquet, расхождение попадает в warnings |
| `schema.primary_key` | подсказка для `group_column` | предлагается, не выбирается |
| `hints.suggested_targets` | список кандидатов в Task Setup | показывается с причиной и `confidence`; **выбирает человек** |
| `hints.identifier_columns` | предложение исключить из признаков | `ExclusionRecord(source="package_hint")`, отменяемо пользователем |
| `hints.datetime_columns` | кандидаты в `time_column` | подтверждаются собственным детектором |
| `hints.high_cardinality_columns` | вход в оценку `effective_dim` | пересчитывается |
| `profile.*` | карточка датасета | **только показ**; ни readiness, ни leakage, ни applicability на нём не строятся |
| `profile.suspicious_columns` | вход в Leakage Guard как *подозрение источника* | ModelArena проверяет заново уже с известным target и формулирует свой вывод |
| `profile.findings[].drilldown` | ссылка «посмотреть в DataArena» | SQL не исполняется внутри ModelArena |
| `profile.quality_score` | не используется | readiness в ModelArena не сводится к числу (D-10) |
| `lineage.json`, `recipe.json` | карточка датасета | показ происхождения; не исполняются |
| `links.inspect_url_template` | кнопка `Inspect in DataArena` | подстановка имени колонки |

### Про `suspicious_columns` и leakage

Разделение зафиксировано и должно одинаково описываться обеими сторонами:

- **DataArena** без target говорит «колонка подозрительна, потому что …» — и не употребляет
  слово leakage;
- **ModelArena** после выбора target говорит «potential leakage candidate because …» —
  и тоже не утверждает факт.

Пользователь не должен видеть два разных вердикта об одной колонке. Если DataArena пометила
колонку подозрительной, а ModelArena её не подтвердила — в UI это показывается как
«DataArena отметила при подготовке; на выбранном target связь не подтвердилась», а не как
молчание.

## 4. Правила безопасности

Пакет — **недоверенный вход**. Он может прийти файлом откуда угодно.

| Правило | Причина |
|---|---|
| Никакой десериализации кода: pickle, joblib, dill внутри пакета не читаются ни при каких условиях | десериализация исполняет произвольный код |
| Никакого eval/exec выражений из `recipe.json` | то же |
| SQL из `findings[].drilldown` не исполняется | это ссылка для DataArena, а не запрос к нам |
| Лимит на размер архива, на распакованный размер и на число файлов | защита от zip-бомбы |
| Пути внутри архива нормализуются; `..` и абсолютные пути отвергаются | path traversal при распаковке |
| `package_url` скачивается только по явному действию пользователя; схема ограничена http/https; редиректы на файловые схемы запрещены | пакет не должен уметь читать локальные файлы |
| Всё, что прочитано из пакета и показывается в UI, экранируется как текст | поля `name`, `explanation`, `reason` пишет другой сервис |

## 5. Поведение при ошибках

| Ситуация | Реакция |
|---|---|
| `format_version: "2.0"` | Отказ: «ModelArena понимает dataarena.package версии 1.x, в пакете 2.0. Обновите ModelArena.» |
| `format_version: "1.5"` (minor выше) | Читаем. Незнакомые поля игнорируем, в warnings — «пакет собран более новой minor-версией» |
| Не совпал `sha256` части | Отказ. Данные не читаются вообще |
| Нет `schema.json` | Читаем: типы берутся из parquet, `semantic_type` определяется своим детектором |
| Нет `profile.json` | Читаем: профиль считается сами |
| `row_count_exact: false` и расхождение | Предупреждение, работа продолжается |
| Пакет пуст / нет строк | Отказ: обучать нечего |
| Одна колонка | Отказ: нужен хотя бы один признак кроме target |

Формат ошибки — общий для API: `{"error": {"code", "message", "details"}, "detail": "..."}`.

## 6. Golden package

В `contracts/dataset-package/v1/` лежит эталонный пакет — тот же файл, что и в DataArena.
Он источник истины для обеих сторон.

Что он обязан содержать, чтобы быть полезным тестом:

- две части данных (`part-0000`, `part-0001`) — проверка сборки из нескольких файлов;
- колонки всех `semantic_type`: `id`, `numeric`, `categorical`, `datetime`, `boolean`, `text`;
- пропуски хотя бы в двух колонках;
- одну колонку с высокой кардинальностью;
- `hints.suggested_targets` минимум с двумя кандидатами разной `confidence`;
- `profile.computed_on.sampled: false` в основном пакете и вариант с `true` — вторым фикстур-пакетом;
- битый вариант (испорченный `sha256`) и вариант с `format_version: "2.0"` — для негативных тестов.

Изменение формата, ломающее golden package, обязано сопровождаться повышением версии.

## 7. Замечания к контракту (передаются владельцу)

Приняты в [RECONCILIATION.md](../../../DataArena/docs/contracts/RECONCILIATION.md) §2,
здесь — как чеклист к внесению в текст контракта:

1. **`version: { dataset_id, version, parent_version }`** в манифесте. Без него нельзя связать
   эксперименты, поставленные на разных версиях одного датасета, — а это ровно то, что нужно
   для сравнения «до/после правки данных».
2. **`links.inspect_url_template`** — обратная навигация.
3. **Pull-транспорт**: DataArena отдаёт URL, ModelArena скачивает. DataArena не должна знать
   про очереди и авторизацию ModelArena.
4. **Явный запрет исполняемой сериализации** внутри пакета — в тексте контракта, а не только
   в правилах потребителя.
5. **Формулировка «`hints` и `profile` — advisory»** в самом контракте: иначе следующий
   потребитель построит на чужом профиле свои решения.
6. **Golden package** в обоих репозиториях + негативные фикстуры (§6).

До внесения и утверждения объединённой версии ModelArena читает только golden package
и не включает импорт по URL (риск T-1 в [DESIGN.md](../DESIGN.md) §11).

## 8. Согласование с владельцем контракта — 2026-09-06

Ответы на вопросы, заданные стороной DataArena при подготовке финальной спецификации
`contract/dataset-package-v1.0.0`.

### 8.1 Ответ A — `__row_id__` и порядок строк

Разделяем три разных вещи, которые легко слипаются:

| Уровень | Где живёт | Назначение |
|---|---|---|
| **Порядок строк** | **в контракте** | делает позицию строки воспроизводимой для обеих сторон |
| `row_key` | **в контракте, опционально** | устойчивая ссылка на строку между сервисами |
| `__row_id__` | только внутри ModelArena | join предсказаний контендеров |

**Порядок строк обязан быть в контракте** — и не ради drilldown, а потому что без него
не воспроизводится сам fingerprint (п. 5 предложения владельца). Требуется зафиксировать:

1. части конкатенируются строго в порядке `manifest.data.files`;
2. внутри части сохраняется порядок строк файла;
3. порядок колонок — как в `schema.json`, не алфавитный;
4. производитель не имеет права переупорядочивать строки между сборкой профиля и записью данных.

**`row_key` — опциональное поле контракта**, объявляющее устойчивый бизнес-ключ строки:

```jsonc
"data": { "row_key": ["customer_id"] }        // часто совпадает с schema.primary_key
```

Если он есть, ModelArena показывает в Head-to-Head и Error Analysis именно его, а кнопка
`Inspect in DataArena` ссылается по ключу, а не по позиции. Ключ **не становится признаком**
(инвариант I-8) и в матрицу обучения не попадает.

**`__row_id__` остаётся внутренним.** Это позиция в снимке ModelArena; `row_index.parquet`
частью пакета не является и наружу не отдаётся. Ссылаться на позицию между сервисами
опасно: любая перепаковка или фильтрация в DataArena сдвинет позиции, а ссылка останется
внешне валидной — это тихая ошибка, которая хуже явной.

### 8.2 Ответ B — лимиты

Единого числа «на пакет» быть не должно: метаданные и данные — разные по природе входы.

| Что | Лимит | Кто задаёт |
|---|---|---|
| `manifest.json` | 1 МБ | контракт |
| каждая из частей `schema` / `profile` / `lineage` / `recipe` | 16 МБ | контракт |
| суммарно метаданные | 64 МБ | контракт |
| число файлов в архиве | 10 000 | контракт |
| коэффициент распаковки | ≤ 100:1 | контракт |
| вложенные архивы | запрещены | контракт |
| **данные (`data/*.parquet`)** | **лимита в контракте нет** | конфигурируется потребителем |

Жёсткий предел на данные в контракте неуместен: датасет законно бывает огромным, а Parquet
читается частями. ModelArena применяет **свой** предел — по умолчанию 5 ГБ распакованных
данных, переменная `MARENA_MAX_PACKAGE_DATA_BYTES`, — и при превышении отказывает
с внятным сообщением, а не падает по памяти.

Лимиты на метаданные обязаны быть в контракте, потому что JSON разбирается целиком в память
до всякой проверки — это и есть поверхность атаки. `manifest.json` читается первым,
поэтому его предел самый жёсткий.

### 8.3 Ответ C — recipe и lineage раздельно

Согласны. Разделение проходит по направлению времени, и это не косметика:

- `lineage.json` — **свидетельство о прошлом** этого пакета; ModelArena только показывает;
- `recipe.json` — **исполняемая инструкция на будущее**, применяется к новым файлам;
  ModelArena **не исполняет его никогда**.

Просьба, необязательная и не блокирующая: флаг `recipe.derived_from_lineage: true|false`.
Рецепт, отредактированный руками и разошедшийся с фактической историей — реальная ловушка,
и дешевле отметить это одним полем, чем сверять граф с шагами.

### 8.4 Ответ D — несовпадение fingerprint

> ⚠️ **Заменено решением владельца** ([D-14](../DECISIONS.md#d-14-два-уровня-идентичности-checksum-артефакта--fingerprint-датасета)).
> Требование жёсткого отказа сохранено, но fingerprint считается по **логическому**
> содержимому, а не по каноническому Arrow IPC. Действующая формулировка — §9.3.
> Раздел оставлен как запись обсуждения.

**За жёсткий отказ.** Но проверки две, и у них разная природа:

| Проверка | При несовпадении | Обход |
|---|---|---|
| `sha256` отдельного файла пакета | отказ, чтение прекращается | нет и не будет |
| `fingerprint` датасета (схема + содержимое) | отказ | нет |

Условие, без которого жёсткий отказ по второй проверке опасен: **канонизация должна быть
дописана до байта**, иначе расхождение версий Arrow превратится в отказ на каждом импорте,
и виноват будет не пакет.

Требуется зафиксировать в контракте:

1. `fingerprint.algorithm: "arrow-ipc-canonical/1"` в манифесте — смена алгоритма становится
   сменой версии, а не загадочной ошибкой;
2. поток канонизируется: без сжатия, без dictionary encoding (или с явной нормализацией
   словарей), фиксированный padding;
3. `custom_metadata` схемы в хеш **не входит** — там оседают версии библиотек;
4. порядок колонок и строк — по §8.1;
5. тип колонки входит в хеш наравне с именем (`int32` и `int64` — разные данные);
6. golden package прогоняется в CI **минимум на двух версиях pyarrow/polars** — это
   единственный способ доказать, что «побайтово воспроизводимо» действительно так.

Если пункт 6 окажется невыполнимым, честнее хешировать логическую каноническую форму
(поколоночное типизированное представление с заданным порядком), чем сериализованный поток.

### 8.5 По десяти решениям владельца

Согласны со всеми десятью. Два уточнения:

**Коллизия имён.** В сообщении фигурирует `package_version` как semver-строка версии формата,
а пункт 6 вводит версию датасета (`version_id`). Это два разных счётчика, и их нельзя называть
похоже. Просим оставить `format_version` для версии контракта, а версию датасета держать
в отдельном блоке `version: { dataset_id, version_id, parent_version_id }`.

**Fingerprint по Arrow IPC — лучше нашего предложения по CSV**, принимаем; условия — §8.4.

### 8.6 Golden package: негативные фикстуры

К основному пакету нужны четыре отрицательных — без них проверяется только счастливый путь:

1. испорченный `sha256` одной части → ожидается отказ;
2. `format_version: "2.0"` → ожидается отказ с указанием понимаемой версии;
3. `format_version: "1.5"` → ожидается чтение с предупреждением и игнорированием незнакомых полей;
4. `profile.computed_on.sampled: true` → ожидается плашка в UI и запрет выдавать статистики за точные.

Плюс минимальный пакет: только `manifest.json` + одна часть данных, без `schema`, `profile`,
`lineage` и `recipe` — проверка, что опциональное действительно опционально.

## 9. Решения владельца проекта перед freeze — 2026-09-06

Действующая редакция. При расхождении с §8 прав этот раздел.

### 9.1 Идентичность строк и колонок

- порядок строк, частей и колонок — часть canonical dataset representation, фиксируется контрактом;
- обязательный `__row_id__` в пользовательские данные **не добавляется**;
- `data.row_key` — опциональное поле контракта для устойчивого business/entity key;
- ModelArena заводит **собственный** immutable `sample_id` после импорта: он нужен для OOF-предсказаний,
  Head-to-Head и drilldown, но **частью контракта не является** и наружу не отдаётся.

Именование внутри ModelArena: в [DESIGN.md](../DESIGN.md) §2 и §5 этот идентификатор
обозначен как `__row_id__`. Смысл совпадает с `sample_id`; переименование — вопрос кода, не контракта.

### 9.2 Лимиты

Security limits формата (контракт) и operational limits потребителя разделены.

| Контракт (security) | Значение |
|---|---|
| `manifest.json` | ≤ 1 MiB |
| отдельная часть метаданных | ≤ 16 MiB |
| суммарно метаданные | ≤ 64 MiB |
| число файлов | ≤ 10 000 |
| коэффициент распаковки | ≤ 100:1 |
| вложенные архивы | запрещены |

Размер data artifact контрактом **не ограничивается**. ModelArena задаёт свой operational limit:
по умолчанию **5 GiB**, переменная `MARENA_MAX_PACKAGE_DATA_BYTES`, обязательно конфигурируемо.

### 9.3 Fingerprint — логический, не сериализационный

Действующее решение — [D-14](../DECISIONS.md#d-14-два-уровня-идентичности-checksum-артефакта--fingerprint-датасета).

```
SHA-256 файла        →  «это именно тот файл, который положила DataArena?»
Dataset fingerprint  →  «это именно тот набор данных?»
```

Два уровня не смешиваются. Один и тот же датасет с другим compression или другой раскладкой
row-group даёт другой SHA-256 файла и **тот же** fingerprint.

| Входит в fingerprint | Не входит |
|---|---|
| имена колонок в порядке | версия pyarrow |
| canonical logical dtypes | метаданные writer |
| порядок колонок и строк | compression |
| позиции null | раскладка row-group |
| каноническое представление значений | метаданные файловой системы |
| число строк и колонок | произвольный `custom_metadata` |

Манифест несёт `fingerprint: { algorithm, value }` с версионированным id алгоритма.

**Реакция ModelArena на несовпадение — жёсткий отказ в обоих случаях, без обходов:**

| Проверка | При несовпадении |
|---|---|
| SHA-256 отдельного файла пакета | отказ, чтение прекращается; сообщение говорит «целостность файла» |
| logical fingerprint датасета | отказ; сообщение говорит «содержимое датасета не соответствует манифесту» |

Тексты ошибок обязаны различаться: это разные причины, и путать их при разборе инцидента дорого.

**Что требуется от спецификации алгоритма**, чтобы отказ был честным (передано владельцу контракта):

1. `canonical value representation` расписана побайтово для каждого logical dtype.
   Явного решения требуют: float (NaN, `-0.0` против `0.0`, denormals), decimal (масштаб),
   timestamp (единица и таймзона), строки (нормализация Unicode), boolean,
   пустая строка против null;
2. правило сборки потока: значение префиксуется тегом типа и длиной (иначе `"ab"+"c"`
   и `"a"+"bc"` дадут один хеш), null — отдельным тегом, а не отсутствием значения;
   в заголовке — число строк, число колонок, имена и dtypes в объявленном порядке;
3. если построчный хеш окажется узким местом на больших датасетах — разрешить в спецификации
   параллельное вычисление по частям с детерминированной сборкой
   `sha256(header || h(part0) || h(part1) || …)`; порядок частей уже зафиксирован §9.1.

### 9.4 Совместимость

| Ситуация | Реакция |
|---|---|
| незнакомое **опциональное** поле в совместимой мажорной версии | игнорировать |
| более новая совместимая minor-версия | читать, предупредить |
| неподдерживаемая мажорная версия | hard reject |
| незнакомая **обязательная** семантика | hard reject |

Minor-добавления не должны ломать старого потребителя — это проверяется фикстурой `1.5`.

### 9.5 Golden package: полный состав фикстур

Заменяет список §8.6 (он был подмножеством).

**Positive:**

1. полный валидный пакет;
2. минимальный валидный пакет;
3. пакет без опциональных `profile` / `hints` / `recipe`;
4. multipart-датасет, если multipart поддерживается.

**Negative:**

1. испорченный SHA-256 артефакта;
2. испорченный logical fingerprint;
3. неподдерживаемая мажорная версия;
4. более новая совместимая minor-версия;
5. `profile.computed_on.sampled: true`;
6. некорректная schema;
7. отсутствующий обязательный артефакт;
8. дублирующиеся / конфликтующие записи в манифесте;
9. попытка archive traversal;
10. нарушение лимита распаковки.

Фикстуры 9 и 10 — не «на всякий случай»: пакет приходит файлом откуда угодно (§4),
и это единственная защита распаковщика.

### 9.6 Критерий freeze и разблокировка Stage 1

```
DataArena producer tests  PASS
ModelArena consumer tests PASS
        на одном и том же golden package
                  ↓
        Dataset Package v1 = FROZEN
                  ↓
   обе стороны фиксируют format_version
   breaking-изменения — только следующей major
                  ↓
        Stage 1 параллельно с обеих сторон
```

До этого **Stage 1 не начинается** ([D-15](../DECISIONS.md#d-15-критерий-freeze-контракта-и-разблокировки-stage-1),
риск T-1 в [DESIGN.md](../DESIGN.md) §11).

Consumer tests, которые обязаны пройти, — таблица §1 плюс по одному тесту на каждую
негативную фикстуру §9.5.
