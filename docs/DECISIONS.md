# Принятые решения (ADR log)

Решения, зафиксированные владельцем проекта. Изменение любого из них требует правки этого файла
и пересмотра затронутых документов. Ссылка на решение в коде и обсуждениях — по номеру: `D-3`.

Дата фиксации D-1…D-10: 2026-09-06.

---

## D-1. База ранжирования — CV mean

`cv_mean` по фолдам — **единственная** основа leaderboard, выбора Champion и tuning.

Holdout — финальное подтверждение качества уже выбранных моделей. Holdout **нельзя**
использовать для model selection и подбора гиперпараметров.

**Почему:** ранжирование по holdout — это подбор модели под test. Через 8 контендеров
и 30 trials Optuna holdout перестаёт быть независимой оценкой, а пользователь об этом не знает.

**Как проверяется:** тест `test_holdout_never_used_for_ranking` — доступ к holdout-части
обёрнут счётчиком, при tuning счётчик обязан остаться нулевым.

## D-2. Бустеры — optional extras

Ядро ModelArena ставится и работает **только на зависимостях sklearn**.
XGBoost / LightGBM / CatBoost подключаются через adapter/plugin system как extras.

```
pip install modelarena                # ядро: sklearn
pip install modelarena[boosters]      # + xgboost, lightgbm, catboost
```

В UI недоступный адаптер показывается как contender со статусом `unavailable`
и текстом, что именно поставить. Молча исчезать он не имеет права.

## D-6. Predictions-first architecture

OOF- и holdout-предсказания сохраняются как **first-class артефакты эксперимента**.

Пересчёт leaderboard, смена objective weights, Head-to-Head, calibration, error analysis
и любая post-hoc диагностика **не должны требовать переобучения**.

**Следствие для API:** `GET /runs/{id}/leaderboard?objective=…` — чистое чтение,
никаких job. Ответ за миллисекунды, а не за минуты.

## D-7. Fairness protocol

Одинаковы для всех контендеров:

- split и индексы фолдов;
- seed;
- набор признаков;
- evaluation protocol;
- набор метрик.

Препроцессинг **может различаться** между семействами моделей, если это нужно для их
корректной работы. «Одинаковый preprocessing для всех» требованием честности не является.

**Как проверяется:** `fold_assignment_hash` в `run.json` обязан совпадать у всех контендеров;
профиль препроцессинга каждого контендера записывается и виден в UI.

## D-8. Canonical format — Parquet

Внутреннее представление датасета в ModelArena — Parquet + Polars в памяти.
pandas — только на границе sklearn.

CSV и прочие форматы допускаются как input, но после импорта приводятся к canonical
representation с сохранением schema и fingerprint.

**Почему:** CSV теряет dtypes. Дата, ставшая строкой, молча ломает и выбор temporal split,
и препроцессинг.

## D-9. DataArena hints и profile — advisory only

Всё, что пришло в пакете как статистика или подсказка, показывается пользователю
с указанием источника, но **любое решение** (readiness, leakage, выбор протокола, applicability)
ModelArena считает сама по `data/*.parquet`.

`sha256` частей и мажорная версия формата валидируются обязательно.
`profile.computed_on.sampled: true` обязано быть видно в интерфейсе.

## D-10. Dataset Readiness — без искусственного score

Никаких 0–100. Explainable statuses:

```
READY | CAUTION | HIGH RISK
```

с конкретными причинами и расчётами («минорный класс 14 объектов → ≈2.8 на фолд при 5-fold»),
а не с абстрактными порогами.

Quality Score из AutoDataAnalysis остаётся в DataArena и в ModelArena не переносится.

## D-13. Standalone-приём файлов разрешён

Добавлено 2026-09-06. Снимает противоречие между ТЗ §1 («поддержка standalone обязательна»,
«принимать dataset напрямую») и формулировкой [SCOPE.md](SCOPE.md) §1
(«не читает сырые файлы пользователя»).

ModelArena **принимает** табличный файл напрямую (`.parquet`, `.csv`, `.json`, `.jsonl`, `.xlsx`)
и превращает его в такой же внутренний снимок, как из пакета.

ModelArena **не редактирует** данные: нет join, нет SQL IDE, нет правки ячеек, нет экспорта
преобразованных данных. Формулировка SCOPE §1 читается как запрет на редактирование,
а не на чтение.

Импортированный файл помечается `source: "file"`, и в UI рядом стоит подсказка:
подготовка данных — в DataArena.

## D-14. Два уровня идентичности: checksum артефакта ≠ fingerprint датасета

Зафиксировано владельцем 2026-09-06. **Заменяет** и исходное предложение DataArena
(хеш по Arrow IPC), и наш ответ в
[dataset-package-consumer.md](contracts/dataset-package-consumer.md) §8.4.

```
SHA-256 файла        →  «это именно тот файл, который положила DataArena?»
Dataset fingerprint  →  «это именно тот набор данных?»
```

Это разные вопросы, и смешивать их нельзя. Один и тот же датасет, записанный Parquet
с другим compression или другой раскладкой row-group, даёт **другой** SHA-256 файла
и **тот же** fingerprint.

Fingerprint считается по **логическому содержимому** и обязан быть воспроизводим независимо
от версии pyarrow, Parquet writer, compression, dictionary encoding, сериализации метаданных
и физической раскладки файлов.

Входит в хеш: имена колонок в порядке, canonical logical dtypes, порядок колонок,
порядок строк, позиции null, каноническое представление значений, число строк, число колонок.

Не входит: версия pyarrow, метаданные writer, compression, раскладка row-group,
метаданные файловой системы, произвольный `custom_metadata`.

Манифест несёт `fingerprint: { algorithm, value }` с версионированным идентификатором
алгоритма (например `dataarena-logical-sha256-v1`). Алгоритм описывается достаточно точно,
чтобы независимый потребитель реализовал его без импорта кода DataArena.

**Почему изменено:** хеш сериализованного потока привязывает идентичность данных к версии
библиотеки. При выбранном жёстком отказе по несовпадению (§8.4) обновление pyarrow у любой
из сторон ломало бы каждый импорт, и виноват был бы не пакет.

## D-15. Критерий freeze контракта и разблокировки Stage 1

Зафиксировано владельцем 2026-09-06.

Dataset Package v1 считается **FROZEN**, когда на **одном и том же** golden package
одновременно проходят:

```
DataArena producer tests  PASS
ModelArena consumer tests PASS
```

После freeze: обе стороны фиксируют `format_version`; breaking-изменения — только следующей
мажорной версией; обе сессии начинают Stage 1 параллельно.

**До freeze Stage 1 не начинается ни одной стороной.** Это снятие риска T-1
([DESIGN.md](DESIGN.md) §11): если обе стороны начнут писать код против неутверждённого
контракта, переделывать придётся оба конца.

Состав golden package (positive и negative фикстуры) — в
[dataset-package-consumer.md](contracts/dataset-package-consumer.md) §9.4.

Правила совместимости, которые ModelArena обязана соблюдать:

| Ситуация | Реакция |
|---|---|
| незнакомое **опциональное** поле в совместимой мажорной версии | игнорировать |
| более новая совместимая minor-версия | читать, предупредить |
| неподдерживаемая мажорная версия | hard reject |
| незнакомая **обязательная** семантика | hard reject |

### Статус: FROZEN, 2026-09-06

Все пять условий выполнены и проверены с нашей стороны запуском, а не по отчёту:
producer- и consumer-реализации дали совпадающие вердикты и коды на всех четырнадцати
фикстурах, зеркало побайтово идентично каталогу владельца (91 файл), тег
`contract/dataset-package-v1.0.0` стоит в обоих репозиториях и указывает на `ea47720`;
контракт на теге совпадает с `main`.

**Stage 1 разблокирован.** Breaking-изменения формата — только следующей мажорной версией.

### Финальный критерий (редакция владельца, 2026-09-06)

1. producer/reference-набор DataArena — PASS;
2. независимая consumer-проверка ModelArena — PASS;
3. полная матрица фикстур — PASS, **включая** случай расхождения схемы с данными;
4. оба репозитория указывают на одну и ту же версию спецификации;
5. только после этого — **одновременная** установка тега `contract/dataset-package-v1.0.0`
   в обоих репозиториях.

Тег, поставленный раньше выполнения всех пяти условий, снимается: он утверждал бы freeze,
которого не было. Прежний тег удалён из обоих репозиториев по этой причине.

## D-16. Отпечаток — самостоятельный версионированный протокол

Зафиксировано владельцем 2026-09-06.

`dataarena-logical-sha256-v1` — не «хеш пакета», а **отдельный контракт со своей версией**.
Идентификатор алгоритма живёт в манифесте (`content_fingerprint.algorithm`) и меняется
независимо от версии формата пакета.

**После freeze семантика внутри идентификатора не меняется никогда.** Даже если найдётся
более удачная канонизация `decimal`, `datetime` или Unicode — это `…-v2` с новым
идентификатором, а не правка существующего.

**Почему:** отпечаток — это идентичность датасета, записанная в карточках экспериментов
и в артефактах моделей. Изменение семантики под тем же именем означает, что все ранее
сохранённые отпечатки начинают означать что-то другое: старые эксперименты перестают
сходиться со своими данными, а причина выглядит как «пакет битый».

**Как применяется в ModelArena:** `DatasetSnapshot` хранит `fingerprint` вместе
с идентификатором алгоритма. Неизвестный идентификатор — отказ (D-14), а не попытка
пересчитать «как умеем». Сравнение отпечатков, посчитанных разными алгоритмами,
запрещено на уровне кода.

## D-17. Что можно править в контракте после freeze без повышения версии

Добавлено 2026-09-06 по итогам вопроса владельца контракта: текст D-16 внесён
в спецификацию уже после установки тега, версия оставлена `1.0.0`.

**С решением согласны.** D-16 — правило управления изменениями, а не правило формата:
оно запрещает то, что и так не предполагалось, ни один существующий пакет от него
не становится невалидным, фикстуры не пересобирались, отпечаток golden прежний,
ни producer, ни consumer не меняют поведения.

Но из этого следует расхождение, которое нужно назвать вслух: **тег помечает состояние,
которое обе стороны провалидировали, а `main` содержит правки поверх.** Без правила
это расхождение будет расти по одной «безобидной» правке за раз.

Правило:

| Что правится | Версия | Что требуется |
|---|---|---|
| пояснения, обоснования, журнал решений, правила управления изменениями | не меняется | ничего |
| формулировка нормативного требования без изменения его смысла | PATCH | перечитать обеими сторонами |
| любое нормативное требование, JSON Schema, фикстуры, эталонные реализации, алгоритм отпечатка | минимум PATCH, при несовместимости MAJOR | пересборка golden, прогон обеих матриц, **перенос тега** |

Что считается авторитетным при расхождении: **тег** — для реализаций,
`main` — для чтения человеком. Если тег и `main` разошлись нормативно, это дефект,
а не состояние.

Просьба к владельцу контракта — внести это правило в §E, чтобы оно было общим,
а не только нашим.

### Уточнение D-17 по первому применению, 2026-09-06

Правило проверено на реальном случае сразу после записи: сверка тега с `main` показала,
что в контракте появился новый файл `reference/run_matrix.py` — 87 строк, добавление,
без единой правки `fingerprint.py` и `validate_package.py`.

По букве правила `reference/` — эталонная реализация, значит требуется PATCH и перенос тега.
По смыслу — добавлен прогонщик матрицы, который ничего не решает: он вызывает существующие
проверки и не может изменить вердикт по пакету.

Уточнение: версионированным событием является изменение **поведения** контракта, а не факт
правки файла в каталоге. Добавление вспомогательного инструмента (прогонщик, скрипт сборки,
проверка воспроизводимости) версию не двигает, **если** нормативные модули не менялись
и матрица фикстур даёт прежний результат — и то, и другое проверяется запуском, а не на глаз.

Иначе правило начинает требовать церемонии там, где риска нет, а правило, требующее
бессмысленной церемонии, перестают соблюдать целиком.

Проверено: `fingerprint.py` и `validate_package.py` между тегом и `main` идентичны,
матрица на текущем `main` — 14 из 14.

## D-18. Транспортный слой различает четыре причины неудачи

Зафиксировано владельцем 2026-09-06 после того, как параллельная сессия поймала
это ручной проверкой: остановленный backend через прокси Vite приходил на фронт
как пустой `500`, и пользователь видел «Backend вернул пустой ответ» вместо
«запустите backend».

Клиент обязан различать:

| Причина | Что показывается |
|---|---|
| backend недоступен, соединение отклонено | «ModelArena backend недоступен. Запустите backend и повторите» |
| таймаут | «Backend не ответил за N секунд» — с возможностью повторить |
| backend вернул структурированную ошибку API | сообщение и код из ответа как есть |
| ошибка прокси или самого фронта | «Сбой на стороне интерфейса», код `frontend_error` |

Правила:

- **не показывать `500` и «пустой ответ»** как конечное объяснение;
- **не маскировать недоступность backend под ошибку валидации датасета** — пользователь
  начнёт чинить данные вместо того, чтобы запустить сервис;
- **повтор — явное действие пользователя**, а не автоматический цикл: молчаливый ретрай
  скрывает причину и удлиняет ожидание.

Формально оба случая — валидный ответ с кодом 500. Различить их можно только тем,
что собственный backend **всегда** отдаёт непустое тело в формате контракта ошибок.

## D-19. Предупреждение обязано объяснять, а не подсвечивать

Backend отдаёт предупреждения о выполнимости протокола, структуре данных, тонком фолде,
редком классе. Интерфейс **не имеет права** превращать их в декоративные жёлтые плашки.

Каждое предупреждение отвечает на три вопроса:

1. **что обнаружено** — с числами, а не «возможны проблемы»;
2. **почему это важно** — что именно исказится в результате;
3. **что можно сделать** — конкретное действие или явное «ничего, просто учитывайте».

Предупреждение, на которое нельзя отреагировать, обязано это признавать. Плашка без
третьего пункта обучает пользователя игнорировать все плашки подряд, включая те,
которые важны.

## D-20. Регрессионный тест считается защитой только если краснеет при снятии проверки

Зафиксировано владельцем 2026-09-07 по итогам adversarial-review этапа 1.

Тест, который остаётся зелёным после удаления проверки, которую он якобы защищает,
защитой не является — он лишь фиксирует, что функция вызывается.

**Правило:** для находок уровня HIGH и CRITICAL и для сложных инвариантов безопасности
мутация обязательна: проверка снимается, тест обязан покраснеть, проверка возвращается.
Результат мутации записывается рядом с находкой.

Мутировать каждый тест всегда не требуется — это дорого и не окупается на простой логике.

**Проверено на этапе 1:** снятие `safe_member()` и абсолютного предела распаковки
покраснило ровно три теста из семнадцати — те, что должны.

## D-21. После интерфейса — отдельная ревизия стыка frontend ↔ proxy ↔ API

Зафиксировано владельцем 2026-09-07.

Ревизия backend не покрывает класс дефектов, который появляется только когда
интерфейс начинает разговаривать с сервисом через прокси. Обязательный список
сценариев для второй, короткой ревизии:

| # | Сценарий | Что не должно происходить |
|---|---|---|
| 1 | backend умер посреди запроса | «пустой ответ 500» вместо «сервис недоступен» |
| 2 | старый ответ пришёл после нового | устаревшие данные затирают свежие |
| 3 | двойной клик по загрузке | два импорта одного файла |
| 4 | отмена нажата | кнопка сменилась, а операция продолжилась |
| 5 | структурированная ошибка прошла через транспорт | код и текст потеряны по дороге |
| 6 | интерфейс показал успех | до фактического завершения записи на сервере |
| 7 | огромное тело ошибки | интерфейс не должен падать или зависать |
| 8 | обновление страницы во время загрузки | остаётся состояние-зомби |

Каждый сценарий проверяется **вручную на живой паре сервисов**, а не только тестом:
именно так параллельная сессия нашла дефект с пустым ответом прокси, который
не поймал ни один автотест.

## D-22. Dataset Readiness отвечает на вопрос о сравнении, а не о качестве данных

Зафиксировано владельцем 2026-09-07 перед началом этапа 2.

Readiness отвечает **не** на вопрос «насколько хороший этот датасет», а на вопрос:

> Можно ли честно сравнивать модели на этом датасете при **выбранной задаче**
> и **выбранном протоколе**?

Отсюда главное следствие: вход — не датасет, а **тройка**
`DatasetSnapshot + TaskSpec + EvaluationProtocol`. Проверка датасета в отрыве от задачи —
это data-quality dashboard, и он остаётся в DataArena.

### Статусы

```
READY | CAUTION | HIGH_RISK | BLOCKED
```

`BLOCKED` — когда честное сравнение невозможно в принципе, а не когда результат
выглядит плохо.

### Форма находки

Каждая находка несёт полный набор полей; ни одно не факультативно:

| Поле | Смысл |
|---|---|
| `code` | машинный идентификатор проверки |
| `severity` | `info` / `caution` / `high_risk` |
| `scope` | `dataset`, `target`, `column:<имя>`, `protocol` — к чему относится |
| `observed_value` | что **измерено** на этих данных |
| `threshold` | с чем сравнивалось и почему порог такой при данном `n` |
| `explanation` | что обнаружено |
| `consequence` | что именно исказится в результате сравнения |
| `suggested_action` | что можно сделать; «ничего, просто учитывайте» пишется словами |
| `blocking` | делает ли находка сравнение невозможным |

### Запрещено

- сводить находки в число от 0 до 100;
- прятать отдельные причины за одним баллом;
- применять универсальный порог без учёта размера выборки;
- превращать предупреждение в блокировку только потому, что оно выглядит страшно.

### Контекстность — обязательна

Одно и то же наблюдение означает разное в зависимости от роли колонки:

| Наблюдение | Когда терпимо | Когда критично |
|---|---|---|
| 30% пропусков в колонке | колонка не выбрана признаком | это цель |
| `customer_id` почти уникален | выбран как колонка группировки — это полезная структура | оставлен признаком — риск утечки |
| в данных есть колонка со временем | выбрано разбиение по времени | разбиение случайное, и время игнорируется |
| редкий класс в 14 объектов | 3 фолда, метрика читается с оговоркой | 10 фолдов: в части фолдов класса не будет вовсе |

## D-23. Leakage Guard: механизм, а не корреляция

Зафиксировано владельцем 2026-09-07 перед этапом 3.

Восемь проверок из AutoDataAnalysis — **источник идей, а не код для переноса**.
Для каждой сначала доказывается: *как именно этот сигнал способен сделать leaderboard
нечестным*. Проверка без ответа на этот вопрос не реализуется.

### Вход

`DatasetSnapshot + TaskSpec + EvaluationProtocol` — как и Readiness. Утечка это свойство
связки, а не колонки: дубликат внутри train безвреден, дубликат, пересекающий границу
train ↔ validation, — конкретный механизм завышения.

### Три уровня доказательности

| Уровень | Что означает | Может ли блокировать |
|---|---|---|
| `structural` | механизм доказан построением: значения совпадают с целью, дубликат фактически пересёк границу фолда | да |
| `evidence` | измерено на данных вне обучающей части, механизм правдоподобен | да, при экстремальных значениях |
| `heuristic` | подозрение по форме: имя колонки, вид значений | **никогда** |

### Запрещено

- считать высокую корреляцию с целью утечкой: сильный честный предиктор существует
  и встречается чаще, чем утечка;
- делать вывод по выборке там, где выборка использовалась только для **отбора кандидатов** —
  подозрение по выборке подтверждается на полных данных, если это вычислительно допустимо;
- обучать что-либо на полном датасете до fold-aware диагностики: инструмент, ищущий утечку,
  не имеет права её создавать;
- сообщать о пересечении групп, если протокол групп-зависимый и группы действительно изолированы.

### Обязательные фикстуры

Положительные: признак равен цели; цель плюс шум; строка кодирует цель; пересечение сущностей;
метка времени после события; пропуск кодирует цель; пересечение дубликатов; производный
признак в регрессии.

**Отрицательные — важнее положительных.** Честный очень сильный предиктор; обычный
идентификатор; законный временной признак; высокая кардинальность; дисбаланс без утечки;
пропуски без связи с целью. Детектор, который кричит на всё, бесполезен: доверять можно
только тому, чьё молчание тоже что-то значит.

Проверяется на binary, multiclass и regression.

### Связь с Readiness

Находки утечки входят в Readiness. Состояние «`READY` при подтверждённой блокирующей
утечке» невозможно по построению, а не по договорённости.

## D-24. Состояние прогона называет причину, а не сводится к «получилось / не получилось»

Принято при реализации этапа 5.

Семь состояний вместо двух, потому что «прогон неполон» бывает по разным причинам,
и склеивать их значит врать о том, что произошло.

| Состояние | Когда | Что означает для результата |
|---|---|---|
| `PENDING` | создан, обучение не началось | ничего нет |
| `RUNNING` | идёт | уже посчитанное доступно немедленно |
| `SUCCEEDED` | **все** запланированные участники завершились успешно | сравнение полное |
| `PARTIAL` | есть хотя бы один результат, но не все участники завершились | посчитанное сравнимо между собой; отсутствующие названы с причиной |
| `FAILED` | пригодного результата нет либо нарушен общий инвариант | сравнивать нечего |
| `CANCELLED` | остановлен пользователем | посчитанное сохранено; неполнота вызвана остановкой |
| `INTERRUPTED` | backend перезапущен во время прогона | продолжение невозможно, завершённое сохранено |

Приоритет причин зафиксирован и проверяется тестом:

1. **упавший baseline перевешивает любые успехи.** Он не использует признаки, поэтому
   его отказ указывает на общий путь данных, а не на модель, и остальные результаты
   в таком прогоне недостоверны;
2. **отмена перевешивает арифметику «сколько успело».** Прогон неполон потому, что его
   остановили, а не потому, что модели проиграли;
3. **`SKIPPED` не входит в знаменатель неудач.** Недоступная библиотека и неуместная
   на этих данных модель определены до старта и с причиной. Иначе прогон с четырьмя
   участниками из десяти выглядел бы провальным, хотя шесть никто не собирался запускать.

`SUCCEEDED` требует, чтобы не было ни одного упавшего или отменённого: leaderboard
из трёх строк вместо шести читается как «остальные проиграли».

## D-25. Контендер обучается в отдельном процессе, но параллелизм внутри него — потоки

Принято при реализации этапа 5 после живого замера.

**Процесс на контендера.** Поток не защищает от трёх вещей, которые умеет нативная
библиотека: зависнуть внутри C++, где Python не получит управление и не проверит флаг
отмены; выесть память так, что упадёт весь backend; упасть по segfault, унеся с собой
FastAPI вместе с уже посчитанными результатами. Отдельный процесс делает остановку
настоящей — его можно завершить — и превращает падение чужого кода в отказ одного участника.

**Потоки внутри процесса.** `n_jobs`, взятый из бюджета, по умолчанию поднимает в sklearn
пул **процессов**. Это вложенный параллелизм: память умножается на число заданий, а пул
переживает своего создателя. Измерено: тот же fit с `n_jobs=2` оставлял процесс живым
дольше 30 секунд против 2 секунд без него, и планировщик считал контендера незавершённым,
хотя результат уже лежал на диске. Внутри контендера параллелизм переведён на потоки,
а число потоков численных библиотек ограничивается переменными окружения **до первого
импорта numpy** — иначе BLAS прочитает их слишком поздно.

Следствие для кода: модуль точки входа дочернего процесса импортирует на своём уровне
только стандартную библиотеку. Проверяется тестом по исходному коду.

**Родитель не доверяет тому, что процесс завершится сам.** Результат на диске —
единственный источник истины о том, что контендер посчитан. Процесс, записавший результат
и продолжающий жить, после отсрочки завершается принудительно, а результат забирается
как обычно.

## D-26. Метрика, которую нельзя посчитать, — это не ноль

Принято при реализации этапа 5. Развитие правила этапа 3 о состоянии «не удалось проверить».

ROC-AUC на фолде с одним классом не равен нулю — он не определён. R² при постоянной цели
не равен нулю — формула делит на ноль. MAPE при нулевой цели не определён. Подставленный
ноль в каждом из этих случаев испортил бы среднее по фолдам и выглядел бы как «плохая
модель» вместо «здесь нечего измерять».

Поэтому метрика возвращается как `value = null` с причиной, а среднее по неполному набору
фолдов сообщает, по скольким именно фолдам оно посчитано.

Метрики считаются **только из сохранённых предсказаний** и единым модулем. Ни один адаптер
не приносит собственное число: расхождение в усреднении, в положительном классе или
в обработке ничьей даёт разницу того же порядка, что и разница между моделями, и leaderboard
превратился бы в сравнение реализаций метрики.

## D-27. Отпечаток эксперимента не включает ресурсы

Принято при реализации этапа 5.

Защита от случайного двойного запуска — **серверная**: блокировка кнопки не спасает
ни от повторной отправки формы, ни от второй вкладки, ни от чужого клиента.

Отпечаток считается по датасету, постановке, протоколу, фактическому разбиению, seed
и составу участников с их параметрами. Число потоков и предел памяти в него **не входят**:
тот же эксперимент на ноутбуке и на сервере — один эксперимент, иначе защита от дубля
перестала бы работать при смене машины.

Совпадение с **активным** прогоном означает повторную отправку — пользователь получает
тот же прогон. Совпадение с завершённым разрешено: это осознанное воспроизведение.

## D-28. Прогресс собирается из наблюдённых фактов

Принято при реализации этапа 5.

Единственная единица работы, факт завершения которой система действительно наблюдает, —
посчитанный фолд. Прогресс это счёт таких фактов: «11 из 20 фолдов», «2 участника из 4».

Внутренний прогресс обучения модель не отдаёт, и выдумывать его нельзя. Полоса, доросшая
до 80% и стоящая там десять минут, хуже честного «фолд 2 из 5»: она обещает то, чего
система не знает.

Если планировать нечего, доли нет вовсе — `completed_fraction` равен `null`, а не нулю.
«Ноль процентов» и «делить не на что» — разные утверждения.
